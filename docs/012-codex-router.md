# 012 Codex 路由与原生控制桥

本功能建立在 [011 本机 Codex 对话监控](011-codex-monitor.md) 的历史事实之上。CodexMonitor 只读本机已持久化会话；CodexRouter 把变化整理成一份简报交给 DSH 主 Session；CodexControl 保存后续任务的优先级、目标历史游标和派发回执。默认关闭会话控制。

## 路由简报

简报优先列需要用户决定的会话、技术异常、需要用户处理的 DSH 工单和子线程历史失败。它从已归纳的会话摘要生成，不包含完整对话正文。首次扫描产生一份基线简报；之后只有人工待办、技术异常、DSH 工单待人阶段、子线程失败等事实变化，才向 DSH 主 Session 再发一份。会话排序、同一请求的消息 ID 和摘要措辞变化不会重复触发。未获用户答复的请求保留提醒；同一会话后续出现技术异常时仍更新异常状态，但不会绕过该请求自动派工。面板标明 Codex 历史快照和 DSH 当前工单状态。

## 会话控制

DSH 主 Session 用 `orchestrator_codex_route` 的 `operation=head` 读取目标主会话，`operation=followup` 排一条后续任务，`reorder` 或 `cancel` 只影响尚未领取的任务。工具要求仍在监控中的未归档主会话、与路由读取一致的最新 item ID、无待用户决定事项、无正在执行的同会话 DSH Ticket。发送文案由宿主根据同一会话摘要生成，并要求目标 Session 重新核对当前任务、把审批交给用户。

自动接单仍遵守 011 的原文证据、历史基线和审批限制。会话控制开启且原生桥心跳新鲜时，符合条件的新失败或技术阻塞优先排给原 Codex 主会话；桥断线或控制关闭时继续使用独立 DSH Ticket。子线程不独立接收控制消息，由主会话处理。

## 原生桥

独立启动的 Codex App Server 能读到同一份已存储历史，但没有证据表明它控制 Codex Desktop 正在运行的 turn。路由因此不通过这个连接调用 `thread/resume`、`turn/steer` 或 `turn/interrupt`。执行桥使用 Codex 应用提供的原生线程工具读取 Desktop 所见状态，并发送路由队列里的后续消息。官方接口说明见 [Codex App Server](https://developers.openai.com/codex/app-server)。

队列位于 `<stateDir>/codex-control/queue.json`，仅本机用户可读。桥每次先检查目标线程、最新 item ID、是否已有新用户消息及审批等待，再领取一条任务；领取时先写 `receipts/<intentId>.json`，之后才发送。发送成功或失败再写最终回执。领取后若结果不明，路由不会自动重发，以免同一指令进入会话两次。桥每轮写 `bridge.json` 心跳，超过 10 分钟未更新时面板显示未连接。

现有原生线程工具支持向目标会话发送后续消息，但没有供此桥直接使用且已验证的 Desktop 硬中断接口。运行中的线程暂不接收队列后续消息；它们空闲后再派发。审批请求仍在 Codex 原界面由用户处理，桥不调用批准或修改审批策略的方法。

关闭面板的自动控制会取消尚未领取的任务，并停止新的原生派发；已经领取或送达的消息不会被撤回。失败或取消的任务只有主路由再次明确排入时才会生成新 intent。
